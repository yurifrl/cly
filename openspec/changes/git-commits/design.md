## Context

CLY is a modular Go CLI with an existing `pkg/llm` package (Anthropic + OpenAI streaming) and Cobra-based module architecture. The project already has a detailed split-commit specification (`docs/SPLIT-SPEC.md`) defining the full pipeline: changeset analysis → batching → LLM planning → validation/healing → preview → execution with rollback.

The user wants a `git wip`-style command: run it, AI figures out how to split changes into clean atomic commits, and it just does it. Speed is the top priority — the whole flow should feel instant.

Currently `pkg/llm` only exposes streaming. For this feature we need a non-streaming `Complete` method that returns the full response (JSON) in one shot — faster for structured output where we don't need progressive display.

## Goals / Non-Goals

**Goals:**
- Sub-5-second typical experience (< 20 files) — from command to commits done
- Parallel LLM batch planning for large changesets
- Safe execution with atomic rollback on failure
- Zero-TUI default mode — pure stdout, no Bubbletea overhead
- Works as `cly git-commits` or `cly gc` (alias)
- Conventional commit messages generated by AI
- `--dry-run` for safe preview, `--yes` for CI/scripting, `--all` for unstaged files

**Non-Goals:**
- Hunk-level splitting (file-level granularity only — hunk splitting adds complexity for marginal value)
- Interactive TUI for reordering/editing the plan (stdout preview + confirm is sufficient)
- Changelog generation (separate concern, separate command)
- Supporting `git add -p` style partial staging within files

## Decisions

### 1. Add `Complete()` to `pkg/llm.Client` interface

**Decision**: Extend the `Client` interface with a `Complete(ctx, systemPrompt, messages) (string, error)` method.

**Rationale**: The planner needs full JSON responses, not streaming. Calling `Stream()` and buffering is wasteful — it adds latency from chunked delivery and channel overhead. A direct completion call is simpler and faster. Both Anthropic and OpenAI SDKs have non-streaming endpoints.

**Alternative considered**: Buffer from `Stream()` — adds ~200ms latency for no benefit on structured output.

### 2. File-level grouping only (no hunk splitting)

**Decision**: Each file goes to exactly one commit group. No splitting a file's hunks across groups.

**Rationale**: Hunk-level splitting requires `git add -p` automation which is brittle and slow. File-level grouping covers 95% of real-world cases and keeps execution simple (`git add <file>`). The SPLIT-SPEC supports hunks but marks them optional.

### 3. Shell out to `git` directly (no go-git)

**Decision**: Use `os/exec` to call `git` for all operations (diff, add, commit, reset).

**Rationale**: `go-git` adds a large dependency and doesn't support all git features reliably. Shelling out to `git` is fast (< 10ms per call), battle-tested, and the user already has git installed. Keeps the binary small.

### 4. Parallel batch planning

**Decision**: When changesets exceed 40K chars, split into batches and send all LLM requests concurrently via goroutines.

**Rationale**: A 50-file changeset might produce 3 batches. Sequential processing = 3× LLM latency. Parallel = 1× latency. With `errgroup`, we get clean error handling and can tolerate individual batch failures.

### 5. Module structure — flat, no sub-packages

**Decision**: Single package `modules/git-commits/` with focused files: `cmd.go`, `changeset.go`, `batcher.go`, `planner.go`, `executor.go`, `preview.go`.

**Rationale**: Follows CLY module conventions. The feature has clear internal phases but they don't need package-level isolation. Keeps imports clean and avoids circular dependency issues.

### 6. Confirmation UX — simple stdin prompt, not Bubbletea

**Decision**: Default mode shows the plan in styled stdout and prompts `Execute? [Y/n]`. No TUI.

**Rationale**: Speed. Bubbletea adds startup overhead and complexity. A simple prompt respects the "deadly fast" requirement. `--yes` skips even the prompt for scripting.

### 7. Recovery strategy — soft reset + cached apply

**Decision**: On execution failure, `git reset --soft <originalHead>` then `git reset` then `git apply --cached < savedDiff>`.

**Rationale**: This restores the exact pre-execution state (HEAD position + staged files). Per SPLIT-SPEC, the diff must end with `\n` to avoid corrupt patches.

## Risks / Trade-offs

- **[LLM produces bad JSON]** → Parse with lenient JSON extraction (strip markdown fences, find outermost `{}`), auto-heal duplicates/gaps, fallback to single-commit on total failure
- **[LLM latency spikes]** → 30s timeout per request; fallback to single conventional commit message on timeout
- **[Large changesets > 100 files]** → Batching handles this, but quality degrades. Acceptable — users should commit more often
- **[No hunk-level splitting]** → A file with mixed concerns (feat + fix) goes in one commit. Acceptable trade-off for speed and reliability
- **[git binary not found]** → Fail fast with clear error message at command start
